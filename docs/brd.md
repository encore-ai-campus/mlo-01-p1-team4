# 자동차 데이터 수집·저장·조회 시스템 BRD

## 1. 문서 개요

### 1.1 문서 목적

이 문서는 현재 구현된 자동차 데이터 시스템의 기능과 동작 기준을 쉽게 설명합니다.

### 1.2 시스템 목적

이 시스템은 중고차 API에서 차량 데이터를 가져와 MySQL에 저장하고, 저장된 차량 데이터와 MongoDB의 FAQ 데이터를 내부 웹사이트에서 확인하기 위해 사용합니다.

### 1.3 현재 구성

현재 시스템은 다음 세 서버로 나뉩니다.

| 번호 | 서버 | 역할 |
|---|---|---|
| 1.3.1 | 웹 서버 | Flask 웹사이트를 실행하고 두 DB의 데이터를 조회합니다. |
| 1.3.2 | MySQL 서버 | 중고차 데이터를 저장합니다. |
| 1.3.3 | MongoDB 서버 | 자동차 회사 FAQ 데이터를 저장합니다. |

세 서버는 같은 내부망에서 통신합니다.

## 2. 전체 데이터 흐름

### 2.1 차량 데이터 흐름

~~~text
중고차 API
    ↓
차량 수집 프로그램
    ↓
필드 변환 및 필수값 검사
    ↓
MySQL project1.car_listing 저장
    ↓
Flask 웹사이트에서 조회
    ↓
차량 목록 화면에 출력
~~~

### 2.2 FAQ 데이터 흐름

~~~text
MongoDB의 brand_faq 컬렉션
    ↓
Flask 웹사이트에서 조회
    ↓
메인 화면의 FAQ 영역에 출력
~~~

### 2.3 프로그램 분리 기준

| 번호 | 위치 | 내용 |
|---|---|---|
| 2.3.1 | first-pj-web | 웹사이트 실행 파일과 화면 파일을 둡니다. |
| 2.3.2 | project | 차량 수집 프로그램 등 데이터 수집 파일을 둡니다. |
| 2.3.3 | MySQL 서버 | 차량 데이터베이스를 운영합니다. |
| 2.3.4 | MongoDB 서버 | FAQ 데이터베이스를 운영합니다. |

## 4. 차량 API 수집 기능

### 4.1 수집 시작

차량 수집 프로그램은 먼저 공개 키 주소에서 API 키를 받아옵니다.

### 4.2 차량 페이지 요청

받은 API 키를 요청 헤더에 넣어 차량 목록 API를 호출합니다.

| 번호 | 설정 | 현재 기준 |
|---|---|---|
| 4.2.1 | 한 페이지 차량 수 | 20건 |
| 4.2.2 | 요청 제한 시간 | 10초 |
| 4.2.3 | 다음 페이지 요청 대기 | 2초 |
| 4.2.4 | 최대 페이지 수 | 프로그램 설정값까지 처리 |

### 4.3 다음 페이지 처리

4.3.1 API 응답의 다음 페이지 주소를 확인합니다.

4.3.2 다음 페이지 주소가 있으면 저장 완료 후 다음 페이지를 요청합니다.

4.3.3 다음 페이지 주소가 없으면 수집을 종료합니다.

4.3.4 중복 차량이 있어도 수집을 중단하지 않고 다음 차량과 다음 페이지를 계속 처리합니다.

### 4.4 수집 결과 로그

수집 결과는 로그 파일에 기록합니다.

| 번호 | 로그 항목 | 의미 |
|---|---|---|
| 4.4.1 | input_count | API에서 받은 차량 수 |
| 4.4.2 | processed_count | 변환·검증·저장을 처리한 차량 수 |
| 4.4.3 | loaded_count | 새로 추가된 차량 수 |
| 4.4.4 | duplicate_count | 기존 차량번호와 중복되어 갱신된 차량 수 |
| 4.4.5 | run_status | 전체 실행 성공 또는 실패 상태 |

## 6. MySQL 차량 저장

### 6.1 저장 위치

~~~text
데이터베이스: project1
테이블: car_listing
~~~

### 6.2 테이블 기준

6.2.1 차량 한 건은 car_listing 테이블의 한 행으로 저장합니다.

6.2.2 car_id를 기본키로 사용하여 차량을 구분합니다.

6.2.3 필수 컬럼에는 빈 값을 저장하지 않습니다.

6.2.4 지역, 세부 지역, 브랜드, 연식 검색을 위한 인덱스를 사용합니다.

### 6.3 중복 처리

| 번호 | 조건 | 처리 결과 |
|---|---|---|
| 6.3.1 | 처음 들어온 car_id | 새 차량으로 추가합니다. |
| 6.3.2 | 이미 존재하는 car_id | 기존 차량 정보를 최신 값으로 갱신합니다. |

중복 차량이 발견되어도 오류로 종료하지 않습니다.

### 6.4 신규·중복 건수 계산

6.4.1 수집 시작 전에 테이블의 전체 차량 수를 확인합니다.

6.4.2 수집 종료 후 전체 차량 수를 다시 확인합니다.

6.4.3 종료 후 차량 수에서 시작 전 차량 수를 빼서 신규 적재 건수를 계산합니다.

6.4.4 전체 처리 건수에서 신규 적재 건수를 빼서 중복 처리 건수를 계산합니다.

이 계산은 수집 중 다른 프로그램이 같은 테이블에 차량을 추가하거나 삭제하지 않는다는 조건에서 사용합니다.

### 6.5 저장 실패 처리

6.5.1 한 페이지의 차량은 하나의 묶음으로 저장합니다.

6.5.2 모두 정상 처리되면 저장을 확정합니다.

6.5.3 중간에 오류가 발생하면 해당 묶음의 저장 내용을 되돌립니다.

6.5.4 실패한 페이지는 성공으로 계산하지 않고 오류 로그를 남깁니다.

## 7. 차량 데이터 품질 검사

### 7.1 검사 대상

MySQL car_listing 테이블에 저장된 전체 차량을 검사합니다.

### 7.2 검사 항목

| 번호 | 검사 내용 |
|---|---|
| 7.2.1 | 필수값이 비어 있지 않은지 확인합니다. |
| 7.2.2 | 차량번호와 연식이 정수인지 확인합니다. |
| 7.2.3 | 주행거리와 가격이 정수이며 음수가 아닌지 확인합니다. |
| 7.2.4 | 판매 상태가 허용된 세 값 중 하나인지 확인합니다. |
| 7.2.5 | 등록일이 날짜 형식인지 확인합니다. |

### 7.3 검사 결과

검사 결과는 quality_check_output 폴더에 저장합니다.

| 번호 | 결과 파일 | 내용 |
|---|---|---|
| 7.3.1 | processed-cars.json | 검사한 차량 데이터 |
| 7.3.2 | quality-report.json | 통과·실패 건수와 오류 내용 |

오류가 없으면 품질 상태는 PASS, 오류가 있으면 FAIL로 기록합니다.

## 10. 웹 서버 운영

### 10.1 실행 방식

Flask 애플리케이션은 Gunicorn과 systemd를 사용하여 실행합니다.

### 10.2 자동 실행

10.2.1 SSH 접속을 종료해도 웹사이트는 계속 실행됩니다.

10.2.2 EC2가 다시 시작되면 웹서비스도 자동으로 시작됩니다.

10.2.3 웹서비스가 오류로 종료되면 systemd가 다시 시작합니다.

### 10.3 주요 파일 위치

~~~text
/home/ec2-user/
├── first-pj-web/
│   ├── app.py
│   ├── .env
│   ├── requirements.txt
│   ├── templates/
│   │   └── index.html
│   └── static/
└── project/
    └── 차량 수집 프로그램
~~~

### 10.4 DB 접속 설정

웹 서버의 .env 파일에서 다음 값을 관리합니다.

| 번호 | 설정 | 의미 |
|---|---|---|
| 10.4.1 | MYSQL_HOST | MySQL 서버 주소 |
| 10.4.2 | MYSQL_PORT | MySQL 포트 |
| 10.4.3 | MYSQL_USER | MySQL 사용자 |
| 10.4.4 | MYSQL_PASSWORD | MySQL 비밀번호 |
| 10.4.5 | MYSQL_DATABASE | MySQL 데이터베이스명 |
| 10.4.6 | MONGO_URI | MongoDB 접속 주소 |
| 10.4.7 | MONGO_DATABASE | FAQ가 실제로 저장된 데이터베이스명 |

## 11. 내부망과 보안

### 11.1 사용 포트

| 번호 | 연결 방향 | 포트 |
|---|---|---|
| 11.1.1 | 내부 사용자 → 웹 서버 | TCP 8000 |
| 11.1.2 | 웹 서버 → MySQL 서버 | TCP 3306 |
| 11.1.3 | 웹 서버 → MongoDB 서버 | TCP 27017 |

### 11.2 접근 제한

11.2.1 웹 서버의 8000 포트는 내부 사용자만 접근하도록 제한합니다.

11.2.2 MySQL의 3306 포트는 웹 서버와 필요한 수집 서버만 접근하도록 제한합니다.

11.2.3 MongoDB의 27017 포트는 웹 서버와 필요한 내부 서버만 접근하도록 제한합니다.

11.2.4 DB 포트를 인터넷 전체에 공개하지 않습니다.

### 11.3 계정과 비밀번호

11.3.1 웹사이트는 MySQL root 계정 대신 웹 전용 계정을 사용합니다.

11.3.2 실제 비밀번호와 내부 서버 주소를 문서나 공개 저장소에 기록하지 않습니다.

11.3.3 웹 서버의 .env 파일은 다른 사용자가 읽지 못하도록 권한을 제한합니다.

## 12. 오류 확인 기준

### 12.1 차량 수집 오류

API 요청 또는 MySQL 저장에 실패하면 실패 상태와 오류 내용을 수집 로그에 기록합니다.

### 12.2 웹서비스 오류

systemd 로그에서 최근 오류를 확인합니다.

~~~bash
sudo journalctl -u first-pj-web -n 100 --no-pager
~~~

### 12.3 화면 파일 오류

index.html은 Flask가 찾을 수 있도록 templates 폴더에 있어야 합니다.

### 12.4 FAQ가 표시되지 않는 경우

다음 순서로 확인합니다.

| 번호 | 확인 내용 |
|---|---|
| 12.4.1 | .env의 MONGO_URI가 실제 MongoDB 서버 주소인지 확인합니다. |
| 12.4.2 | MONGO_DATABASE가 실제 FAQ 데이터베이스명인지 확인합니다. |
| 12.4.3 | brand_faq 컬렉션에 문서가 있는지 확인합니다. |
| 12.4.4 | FAQ 문서의 필드명이 웹 조회 필드와 일치하는지 확인합니다. |

## 14. 최종 요약

### 14.1 차량 데이터

차량 수집 프로그램이 API 데이터를 가져와 변환하고 검사한 뒤 MySQL car_listing 테이블에 저장합니다.

### 14.2 중복 데이터

새 차량은 추가하고 기존 차량은 최신 정보로 갱신하며, 중복 때문에 전체 수집을 중단하지 않습니다.

### 14.3 FAQ 데이터

웹사이트는 MongoDB의 brand_faq 컬렉션에서 FAQ를 읽어 메인 화면에 표시합니다.

### 14.4 웹사이트

Flask 웹사이트는 차량과 FAQ를 각각 조회하며, Gunicorn과 systemd를 통해 내부망에서 계속 실행됩니다.
